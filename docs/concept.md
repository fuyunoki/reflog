# REFLOG（リフログ） — コンセプト

## 1. 概要

GitHub アカウントを素材に取り込み、**タイムライン（コミットグラフ）を操作して世界を修正する**体験型 Web ゲーム。
プレイヤーが手にする能力は git のコマンド体系そのものであり、遊んでいるうちに git の内部モデルが身につく。

| 項目 | 内容 |
| --- | --- |
| ジャンル | ノベル + タイムライン操作パズル |
| モチーフ | 時間旅行・世界線修正 |
| プラットフォーム | Web（PC 主体、モバイル対応は段階的に） |
| 想定プレイ単位 | 1 ステージ 3〜10 分 |
| 開発方針 | 長期育成前提。ステージはデータ駆動で追加していく |

## 1.5 タイトルの由来

`reflog` は git において「消したはずのものの記録」を辿るコマンドであり、
このゲームの主題そのものである。

- `revert` と `reset` の違い ＝「打ち消す」と「消す」
- 到達不能になったコミットもエンジン内に保持し続ける実装
- ログイン時、ローカルの記録もアカウントの記録も捨てない統合方式

`reflog` は最終章の切り札として解放される。
**その瞬間にタイトルの意味が回収される**という構造を意図している。

なお「世界線修正官」は主人公の職名として残す。

## 2. 世界設定

時間の流れは **タイムライン** として記録されている。
プレイヤーは、異常が発生した世界線を修復する **修正官**。
手にしているのは歴史そのものを書き換える禁じられた術式 —— それが git のコマンド体系である。

## 3. なぜ「時間旅行 × git」なのか

git の全コマンドが、比喩ではなく**構造的に**時間操作と一致するため。
プレイヤーはゲームの都合を覚えるのではなく、git の本当の意味論を学ぶことになる。

| 能力 | ゲーム内の意味 | 物語上の重み |
| --- | --- | --- |
| `branch` | 世界線を分岐させる | 基本の逃げ道 |
| `commit` | 新たな出来事を刻む | 前進 |
| `revert` | 出来事を打ち消す（起きた事実は残る） | 穏当な修正 |
| `reset` | 時点ごと巻き戻す（歴史が消滅する） | 危険。消えた人は誰も覚えていない |
| `merge` | 二つの世界線を統合する | **conflict = 矛盾した現実の発生** |
| `cherry-pick` | 別世界線の出来事を 1 つだけ持ち込む | 「あの世界の彼女の発明だけを、この世界へ」 |
| `rebase` | 歴史の起点そのものを接ぎ木する | 終盤の禁術 |
| `bisect` | 異常が混入した時点を二分探索で特定 | ミステリー章のコア |
| `reflog` | 消し去ったはずの世界線の残滓を辿る | 最終章の切り札 |

## 4. コアループ

1. ステージ開始時、**世界線図（コミットグラフ）**が画面中央に SVG で描かれる
2. ノードをクリックすると、その時点で何が起きたかのシーンが読める（ノベル + 差分ビュー）
3. 「達成すべき世界の状態」が提示される
   - 例:「A が生存しており、かつ B の発明が存在する世界を成立させよ。ただし戦争は起きていないこと」
4. 能力を組み合わせてタイムラインを操作する
   - **手数制限** と **因果負荷**（使いすぎると世界が壊れるリソース）が制約になる
5. 目標状態を満たせばクリア。破壊的な手段でクリアするとエンディングが分岐する

## 5. 設計の背骨: conflict が物語装置になる

merge 時の conflict を、単なるパズルではなく**選択**として提示する。

```
<<<<<<< 現在の世界線
彼女はその日、研究所を去った。
=======
彼女はその日、研究所に残り、そして——
>>>>>>> 回収した世界線
```

> **どちらの現実を採用しますか。**

conflict の解消がそのまま物語の分岐になる。
git を教える構造が、そのままドラマとして機能する —— これがこのゲームの核心である。

## 6. GitHub 連携（アカウント情報の素材化）

診断画面は作らない。**演出として効く場所に絞って**実データを使う。

- **プロローグ**: ユーザー名を入力すると「あなた自身の記録」を照会。実在のリポジトリとコミットが *あなたの過去* としてゲーム内に出現し、チュートリアルステージが自分の実履歴で構成される
- **素材化**:
  - contribution → 因果エネルギー総量
  - 主要言語 → 修正官の適性（解放される能力が変わる）
  - リポジトリ → 訪問可能な世界線
- **最終章**: 「あなた自身のタイムライン」を修正する。メタ構造で締める
- **アカウント未入力でもデフォルト世界線で完全に遊べる**こと（必須要件）

### API 方針

- 未認証の公開 REST API をブラウザから直接呼ぶ
- レート制限は送信元 IP あたり 60 req/h。プロキシせずユーザー IP の枠を使うため、利用者が増えてもサーバ負荷は発生しない
- **要確認**: 企業 NAT 配下の共有 IP では枯渇しうる。フォールバック（デフォルト世界線への誘導）を必ず用意する
- OAuth は後から Gateway 実装の差し替えだけで導入できる設計にしておく

## 6.5 遊びの二層構造

物語の密度と無限性は両立しないため、遊びを二層に分ける。詳細は [progression.md](progression.md)。

| 層 | 内容 | 無限性 | 物語密度 |
| --- | --- | --- | --- |
| **本編** | 手作りの章。JSON を書き続ける | 有限 | 濃い |
| **観測任務** | 自動生成ステージ。難易度が適応的に上下する | **無限** | 薄い（任務ブリーフ形式） |

プレイヤーは GitHub OAuth でログインでき、記録を一生持ち歩ける。
conflict での決断が `RecordedChoice` として積み上がり、後の章の分岐条件になる。
**プレイヤーの記録そのものが「そのプレイヤーが作った世界」になる。**

未ログインでも遊べることは崩さない。ログインは進捗を持ち歩くための機能であり、
遊ぶための条件ではない。

## 6.6 操作の二つの入口

同じ 1 手を、パネルのボタンからもコマンドコンソールからも打てる。いつでも切り替えられる。

| 入口 | 狙い |
| --- | --- |
| パネル | 何ができるかが一覧で見え、概念を掴める。初見でも詰まらない |
| コンソール | `git revert c2` と本物の構文で打つ。実務にそのまま持ち帰れる |

**ボタンで概念を覚え、コンソールで実際のコマンドを覚える**という二段構えにしてある。
教材としての狙いはここにあり、片方だけでは学習が半分で止まる。

どちらの入口も同じ `AbilityCommand` に落ち、その先は完全に共通の経路を通る。
コンソールは `git log` `git status` `git branch` `git reflog` にも応え、出力は本物の git に寄せる。
見慣れた形が実務でそのまま読めることに意味があるため。

## 7. ステージ設計方針

- ステージは JSON で定義し、**シナリオ追加 = JSON 追加**とする
- 定義に含めるもの: 初期グラフ / 目標述語 / 使用可能な能力 / 手数上限 / 因果負荷の上限 / シナリオテキスト
- 章立て（想定）
  - 第 1 章: `commit` `branch` `merge` —— 世界線という概念の導入
  - 第 2 章: `revert` `reset` —— 「消す」ことの代償
  - 第 3 章: conflict —— 矛盾した現実の調停
  - 第 4 章: `cherry-pick` `bisect` —— 異常の特定と移植（ミステリー編）
  - 第 5 章: `rebase` `reflog` —— 禁術と、失われた世界線の回収
  - 最終章: プレイヤー自身のタイムライン

## 8. UI デザイン方針

参考: [heronaiapp.com](https://heronaiapp.com/)（[Land-book 掲載](https://land-book.com/websites/99185-heron-ai-works-inside-your-design-tools)）

Swiss / インダストリアル系。**「時間管理局の観測端末」**としての質感を狙う。
SF 的な青 × グロー表現は陳腐なので避ける。

参考サイトとは見た目だけでなく**情報設計が同型**である点が採用理由。

| Heron | 本ゲーム |
| --- | --- |
| モデルを監視する | タイムラインを観測する |
| 問題を赤でフラグする | conflict・異常世界線をアクセント色で表示 |
| 「あなたの承認を得て」編集を適用 | 破壊的操作（`reset`）の確認ダイアログ |
| `[01]`〜`[04]` の等幅インデックス | コミットハッシュ・世界線 ID |

### デザイントークン

```css
--base:      #B3B3AF;              /* 支配色。コンクリート的なウォームグレー */
--ink:       #282828;              /* 純黒ではないソフトブラック */
--ink-muted: rgba(40,40,40,0.72);  /* 本文 */
--accent:    #FA3600;              /* バーミリオン。唯一のアクセント */
--surface:   #FFFFFF;
--surface-2: #F2F2F1;
--surface-3: #E0E0DA;
--rule:      1px solid #B3B3AF;
--rule-hot:  1px solid #FA3600;    /* 警告・異常時 */
--radius:    0;                    /* 直角。円形バッジのみ 50% */
```

タイポグラフィ規則

| 用途 | 指定 |
| --- | --- |
| 見出し | グロテスク体 / uppercase / weight 600-700 / letter-spacing -0.02em / **line-height 1.0** |
| ラベル・番号 | 等幅 / 約 10px / uppercase / `[01]` 形式 |
| 本文 | 約 12px / `--ink-muted` |

- 参考サイトは全タイポグラフィが vw ベースでスケールしている。実装では `clamp()` を挟まないとモバイルで破綻する
- ホバー時に文字が縦にスライドして入れ替わる演出が入っている
- フォントは `BT Grotesk` が商用限定のため代替する
  - 見出し・本文: `Archivo`（次点 `Inter Tight`）
  - 等幅: `Geist Mono`（**要確認**: Google Fonts 提供有無）／代替 `JetBrains Mono`
- ダークテーマは背景を `#282828` に反転し、アクセントは `#FA3600` のまま維持する想定

## 9. 技術スタックとインフラ

| 項目 | 決定 |
| --- | --- |
| 言語 | TypeScript 統一 |
| フロント | Vue 3 + Vite + Pinia |
| Git 実装 | 自前 Timeline Engine（isomorphic-git は不採用） |
| アーキテクチャ | クリーンアーキテクチャ |
| リポジトリ | npm workspaces モノレポ |
| 静的配信 | Cloudflare Pages（帯域無制限） |
| 拡張レイヤ | Cloudflare Workers + D1（任意） |

### isomorphic-git を採用しない理由

rebase / cherry-pick が標準サポートされておらず、教材上必要な操作を制御できないため。
自前実装なら状態が単なる JSON になり、巻き戻し・目標判定・リプレイ・サーバ側での解法再検証がすべて容易になる。

### Cloudflare を選ぶ理由

- Pages は帯域・リクエストが無制限。GitHub Pages（月 100GB のソフトリミット）、Netlify / Vercel（月 100GB、超過で課金または停止）より条件が良い
- 無料枠超過時に**課金ではなく制限**（リクエストを弾く）となるため、想定外の請求が発生しない
- **数字は要確認**。無料枠は改定されるため着手時に公式を確認すること

### コストがスケールしない構造

重い処理をすべてクライアントに置くことで、利用者が増えてもサーバコストが増えない。

```
ゲーム進行・Timeline Engine の計算・クリア判定 → ブラウザ内（サーバ負荷ゼロ）
GitHub API の取得                            → ブラウザから直叩き（サーバ負荷ゼロ）
Workers を呼ぶのは                            → ランキング送信・UGC 取得など限られた瞬間だけ
```

### Java / Spring Boot を採用しない理由

JVM は常時起動とメモリを要求するため、「無料で無制限に近い運用」という要件を満たすホスティング先が現状ほぼない（**要確認**）。
また Timeline Engine を TypeScript で書けばサーバ側でもそのまま再利用でき、クリア判定の二重実装を避けられる。

## 10. ロードマップ

| Phase | 内容 | 到達点 |
| --- | --- | --- |
| 0 | Timeline Engine コア（commit / branch / merge / revert / reset）+ SVG 可視化 | 1 ステージが手打ちで遊べる |
| 1 | ステージのデータ駆動化、目標述語の判定、手数・因果負荷 | パズルとして成立 |
| 2 | ノベル演出、conflict 解消 UI、第 1 章（3〜5 ステージ） | **体験型ゲームとして人に見せられる** |
| 3 | GitHub アカウント連携（プロローグ・素材化） | コンセプト完成 |
| 4 | `cherry-pick` / `rebase` / `bisect` / `reflog` と後半章 | 教材としての網羅 |
| 5 | ステージエディタ、ランキング、UGC 投稿（サーバ導入） | 継続育成の基盤 |

## 10.5 進行・アカウントの決定事項

| 項目 | 決定 |
| --- | --- |
| 無限性 | 本編（手作り）＋ 観測任務（自動生成）の二層 |
| 生成方式 | 逆算生成。生成時に想定解を実行し、到達状態を目標にする |
| 難易度 | 本編はプレイヤーが選択、観測任務は成績から適応的に調整 |
| 認証 | GitHub OAuth（トークン交換のみ Workers） |
| 未ログイン | 遊べる。ログイン時にローカルの記録を統合する |
| 物語分岐 | conflict の決断を記録し、章の解放条件として参照する |
