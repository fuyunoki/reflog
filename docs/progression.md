# 進行設計 —— 物語・無限性・難易度・アカウント

「永遠に遊べて、物語があり、難易度が合っていて、記録が一生残る」を成立させるための設計。

## 1. 二層構造

濃い物語は手作りでしか作れず、無限性は自動生成でしか担保できない。
両立させるため、遊びを二層に分ける。

| 層 | 内容 | 無限性 | 物語密度 | 実装 |
| --- | --- | --- | --- | --- |
| **本編** | 章立て、密度の高いシナリオ。JSON を書き続ける | 有限（作者の労力次第） | 濃い | `content/stages/*.json` |
| **観測任務** | 自動生成ステージ。難易度が適応的に上下する | **無限** | 薄い（任務ブリーフ形式） | `domain/stage/generator.ts` |

自動生成の物語が薄くなるのは避けられない。
しかし**「任務ブリーフ」という形式にすることで、薄さが不自然にならない**。

> 任務 #4471 — 1974年11月、白鷺観測所で観測異常。
> 分岐は3、矛盾は2箇所。因果負荷の上限は8。修正せよ。

事務的な通信文として書けば、生成物でも世界観を壊さない。
むしろ「修正官の日常業務」として機能し、本編の非日常性を引き立てる。

## 2. 本編の物語構造

### 縦軸

各章はエピソードとして完結しつつ、次の問いを持ち越す。

1. なぜ世界線は壊れるのか
2. 修正官とは何者か
3. 誰が修正官に命令しているのか
4. 最終章 —— プレイヤー自身のタイムライン

この構造なら章を追加し続けられる。ただし**「永遠」は作者が書き続ける限り**であり、
無限性は観測任務が担う。

### 章と能力の対応

物語の進行と、教えられる git の概念を一致させる。

| 章 | 能力 | 物語上の意味 |
| --- | --- | --- |
| 1 | `commit` `branch` `merge` | 世界線という概念の導入 |
| 2 | `revert` `reset` | 「消す」ことの代償 |
| 3 | conflict | 矛盾した現実の調停 |
| 4 | `cherry-pick` `bisect` | 異常の特定と移植（ミステリー編） |
| 5 | `rebase` `reflog` | 禁術と、失われた世界線の回収 |
| 最終 | 総合 | プレイヤー自身の記録 |

### 分岐 —— 決断が世界になる

conflict でどちらの現実を選んだかを `RecordedChoice` として積み上げ、
後の章の解放条件として参照する。

```ts
// 「霧島が昇華した」を選んだプレイヤーにだけ開く章
unlockedBy: {
  type: 'choseValue',
  stageId: 'ch1-01',
  key: 'subject.alive',
  value: 'ascended'
}
```

同じ章の同じ位置に複数の候補を置き、条件に合う最初のものを配信することもできる
（`BranchingEpisode`）。既定ルートは末尾に `{ type: 'always' }` を置く。

**プレイヤーの記録そのものが「そのプレイヤーが作った世界」になる。**
これが GitHub をモチーフにする必然性の完成形でもある —— 履歴が人を表す、という主題が
ゲームシステムとして実装されている。

## 3. 観測任務（自動生成）

### 逆算生成

ランダムに盤面を作って解けるか探索するのではなく、逆から作る。

```
1. 盤面を生成する
2. 想定解を組み立て、実際に実行する
3. 到達した状態を「目標」にする
4. 手数・因果負荷の上限を、想定解の実測値 + 難易度の余裕で決める
```

**生成時点で解を握っているので、解けないステージが原理的に出ない。**
条件を満たさない生成結果は破棄して再試行する（最大 60 回）。

テストで全難易度 × 40 任務 = 160 件を生成し、そのすべてが想定解でクリアできることを
検証している。

### conflict を確実に起こす仕組み

3-way merge の性質上、単に分岐させるだけでは conflict は起きない。
revert したキーは base の値に戻るため、`ours == base` となって相手側が自動採用されてしまう。

そこで main に 2 種類の出来事を置く。

| 出来事 | 役割 |
| --- | --- |
| **異常** | プレイヤーが `revert` する対象 |
| **通常の出来事** | revert されない。これを分岐世界線と衝突させる |

分岐世界線が「通常の出来事」と同じ事実を別の値に変えることで、
`base ≠ ours ≠ theirs` が成立し、conflict が確実に発生する。

### 決定的生成

`seed` が同じなら必ず同じ任務が出る（mulberry32 + FNV ハッシュ）。

- 任務番号を共有するだけで、他人と同じ盤面を遊べる
- **生成したステージをサーバに保存する必要がない**（番号だけ持てばよい）

### 語彙の差し替え

事実キー（`subject.alive` `device.state` `site.state` `record.state`）は固定し、
**表示名だけを毎回差し替える**。

これで生成ロジックは単純なまま、プレイヤーには毎回違う世界に見える。
表示名は `StageSpec.factLabels` / `valueLabels` に入り、Presentation 層だけが使う。

## 4. 難易度

### プロファイル

`DifficultyProfile` が生成器へのパラメータそのものになっている。

| 警戒度 | 分岐 | 深さ | 矛盾 | 解の長さ | 手数の余裕 | 助言 |
| --- | --- | --- | --- | --- | --- | --- |
| 低 (quiet) | 1 | 1–2 | 0–1 | 2–3 | +3 | あり |
| 中 (standard) | 1–2 | 2–3 | 1–2 | 3–4 | +2 | あり |
| 高 (severe) | 2–3 | 3–4 | 2–3 | 4–6 | +1 | なし |
| 特級 (critical) | 3–4 | 4–5 | 3–4 | 5–8 | +0 | なし |

### 適応

本編はプレイヤーが選び、観測任務は成績から自動調整する。

```
直近 3 件で 2 回以上失敗       -> 下げる
ヒント / やり直し / 手数超過あり -> 据え置き
3 件すべて無傷でほぼ最短        -> 上げる
```

**上げるのは慎重に、下げるのは素早く。**
「難しすぎて詰まった」体験のほうが「簡単すぎた」より離脱に直結するため。

## 5. アカウント

### 認証

GitHub OAuth を使う。

- モチーフと一致する（GitHub を題材にしたゲームの認証が GitHub である必然性）
- **パスワードを預からずに済む**
- アカウント情報の素材化（contribution → 因果エネルギー等）とそのまま繋がる

`client_secret` を扱う必要があるため、トークン交換だけは Cloudflare Workers で行う。
これが**本プロジェクトで最初にサーバが必要になる箇所**。

### 未ログインでも遊べることは崩さない

ログインは「進捗を持ち歩けるようにする」機能であって、遊ぶための条件ではない。

```
未ログイン -> LocalStorageProgressRepository
ログイン   -> D1ProgressRepository
```

**ドメインは一切変更不要**。合成ルートで注入する実装を差し替えるだけで済む。
クリーンアーキテクチャにした投資がここで回収される。

### 記録の統合

ログイン時、ローカルの進捗をアカウントへ統合する。どちらかを捨てない。

| 項目 | 統合方法 |
| --- | --- |
| ステージ記録 | ステージごとに良い方（perfect > 手数少 > 負荷少） |
| 決断 | 時系列で束ね、重複のみ排除 |
| 任務成績 | 結合して直近 20 件 |
| 任務番号 | 大きい方 |

> 消してしまえば、誰も悼めなくなる

このゲームの主題に、実装としても従う。

## 6. コスト構造

アカウントを入れてもコストはスケールしない。

| 処理 | 実行場所 | サーバ負荷 |
| --- | --- | --- |
| ゲーム進行・判定 | ブラウザ | なし |
| ステージ生成 | ブラウザ（seed から決定的に生成） | なし |
| GitHub API 取得 | ブラウザ直叩き（ユーザーの IP 枠） | なし |
| 進捗の保存 | Workers + D1 | 1 ユーザー 1 日数回 |

D1 の書き込み無料枠は 10 万行/日（**要確認**：無料枠は改定される）。
1 ユーザーあたり 1 日数回のセーブなら、数万ユーザー規模まで無料枠に収まる計算になる。
